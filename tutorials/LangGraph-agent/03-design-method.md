# 03 · 拆解思路：从需求到可运行的图

这是本材料的核心。前两章是「是什么」，这章是「怎么做」。

---

## 总览

```
Step 0  该不该上图？          ← 最容易被跳过，也最该先问
Step 1  找决策点             ← 一次带出【图】【节点】【State】三样东西
Step 2  设计 State           ← 每个字段问三问
Step 3  划分节点             ← 判据：判断 / 换自主度 / 传数据
Step 4  逐格定自主度          ← 每格问「依据是第几级」
Step 5  骨架先跑通，再填实现
        ↺ 反复回改：图和工具互相拉扯
```

**注意这不是瀑布。** Step 1 和 Step 3 会来回，Step 4 可能推翻 Step 3，Step 5 填到一半可能要回头改 Step 1。

---

## Step 0 · 该不该上图

不是所有需求都该用 LangGraph。上图有代价：多一层抽象、多一堆样板、调试变难。

**同时满足下面三条才上图：**

| 条件 | 反例（不该上图） |
|---|---|
| 流程有 **明显阶段**，阶段之间有先后 | 就一件事要办 → 一个 prompt 搞定 |
| 阶段之间要 **传递数据** | 每步独立、不共享上下文 → 直接串函数 |
| **不是所有步骤都该自主** | 全程都该自主 → 直接上 `create_agent` |

第三条最能说明问题：

> **如果你发现每一格都该放自主，那就别画图了。**

图的价值恰恰在于「**有些格子必须钉死**」。

---

## Step 1 · 找决策点（关键）

**不要从「流程步骤」抽节点，要从「决策点」切。**

为什么？因为 **流程步骤是业务语言，节点是工程语言**。业务上的「审核报销单」是一步，工程上要拆成好几个节点。

### 决策点一次带出三样东西

```
         ┌─ 决策点在哪 ─────→ 就是分叉 ──────→ 决定【图的形状】
决策点 ──┤
         ├─ 两刀之间的段 ───→ 就是一个节点 ──→ 决定【节点划分】
         │
         └─ 决策要看哪些数据 → 就是 State 字段 → 决定【State】
```

**一个切入点，三样东西一次全出来。**

### 走一遍：报销审核

**找决策点：**

| 决策点 | 分叉 | 带出的 State 字段 |
|---|---|---|
| 单据有效吗？ | 无效 → 直接 END | `is_valid`, `invalid_reason` |
| 谁批？（金额 > 5000） | 总监 / 主管 | `amount` |
| 合规吗？ | 不分叉，但决定输出内容 | `check_result` |

**两刀之间的段 = 节点：**

```
[校验] ─决策点1─→ [分类] → [核对] → [写意见] ─决策点2─→ [总监/主管]
```

落到：`validate_receipt` / `classify_expense` / `check_expense` / `draft_opinion` / `notify_director` / `notify_manager`。

**State 字段也跟着出来了：**

```python
class ExpenseState(TypedDict, total=False):
    receipt_text: str; employee: str              # 输入
    is_valid: bool; invalid_reason: str           # 决策点1 要看的
    expense_type: str; amount: float              # 决策点2 要看的
    check_result: Dict                            # 过程产物
    opinion: str; approver: str                   # 输出
```

**注意：这套方法自然长出了实际实现的图。** 不是巧合 —— 因为决策点就是流程的关节。

---

## Step 2 · 设计 State：每个字段问三问

State 不是「罗列需要的数据」，而是 **节点之间的接口**。对每个字段问：

| 问题 | 为什么重要 |
|---|---|
| **谁写它？** | LangGraph 是合并语义，**多个节点写同一字段会互相覆盖** |
| **谁读它？** | 没人读 → 这不是 State，是这个节点的局部变量 |
| **什么时候有值？** | 读取时可能还没写过 → 要 `.get()` 兜底 |

### 铁律：一个字段只有一个「主人」

```python
class ExpenseState(TypedDict, total=False):
    is_valid: bool          # ① 校验节点写 —— 只有它写
    expense_type: str       # ② 分类节点写 —— 只有它写
    check_result: Dict      # ③ 核对节点写 —— 只有它写
```

**这条注释不是文档，是契约。** 没有它，加到第五个节点时你就会开始搞不清谁覆盖了谁。

### 三问的实操结果

| 情况 | 结论 |
|---|---|
| 有人写、有人读 | ✅ 留在 State |
| 有人写、**没人读** | ❌ 删掉 —— 它是节点内部变量 |
| **没人写**、有人读 | ⚠️ 读到的永远是默认值 —— 大概率是漏了写入节点 |

## Step 3 · 节点划分判据

### 判据：边界上有没有发生这三件事

1. 要做 **判断 / 分叉**
2. 要 **换自主度** 或 **换模型**
3. 要 **传递数据**

**三件事一件都没有 → 这两个节点该合并。**

### 两种典型的切错

| 症状 | 后果 | 修法 |
|---|---|---|
| **太细** —— 一个节点干一件事（「抽金额」单独一个节点） | 每多一个节点 = 多一次 LLM 调用 + 多一层状态传递 | 合并到相邻节点 |
| **太粗** —— 「审核报销单」一个大节点包办 | 那还不如直接用 L3 自主 Agent，**图白画了** | 按决策点拆开 |

### 一个自检方法

把节点名连起来念一遍：

```
校验 → 分类 → 核对 → 写意见 → 分发
```

如果念出来是 **业务的阶段**，说明切得对。
如果念出来是「做 A → 做 B → 做 C」这种 **无阶段感的流水账**，说明你有节点该合并。

## Step 4 · 逐格定自主度

对每个节点问 **两个问题**。

### 问题一：这格的判断依据是第几级？

（见 [02 · 判断依据的权威性阶梯](02-autonomy-ladder.md#判断依据的权威性阶梯)）

| 节点 | 能写成代码规则吗？ | 依据级别 | 结论 |
|---|---|---|---|
| 校验 | 不能，「空白 / 无关附件」要语义理解 | 2（人工规则） | **L1** |
| 分类 | 类别能穷举，但识别靠语义 | 2 + 代码兜底 | **L1 + 兜底** |
| **核对** | ← **关键决策**：依据来自哪？<br>只靠文本 → 第 4 级；必须查外部 → 第 3 级 | **看情况** | **看情况** |
| 写意见 | 纯摘要 | 2（硬性规则） | **L1** |
| 审批人 | **能！金额比大小** | 1（纯代码） | **L0，不用 LLM** |

**最后一行是这套方法最值钱的产出**：它告诉你「这一格根本不需要 LLM」。

每找到这样一个格子，就省一次调用、去掉一个不确定源。

### 问题二：这格该用哪个模型？

固定骨架的一个隐藏价值 —— **成本预算可以在图上按节点分配**。

校验 / 分类用便宜小模型，只有核对这种要推理的格子才上贵模型。

> 配套项目为了对比公平，两版所有节点用了同一个模型（`get_llm()` 默认 `deepseek-flash`），**生产上不必如此**。

## Step 5 · 骨架先跑通，再填实现

```
1. 先写图的骨架（节点名 + 边 + 路由函数），节点体全用 print 占位
2. 用假数据跑一遍 —— 确认【数据流】通了、分叉走对了
3. 再逐个把节点体填成真的（先填固定节点）
4. 填到某一格时如果发现「这格需要查外部」，才把它升级成自主
5. 加了工具之后回头看 —— 图要不要拆 / 并？
```

### 为什么不能一上来就设计自主格子

因为你会同时面对两类问题：**流程错了吗？还是这一格自主得不对？** 一锅粥，没法定位。

**先全固定跑通，再升级自主** —— 这也是配套项目 A 版 → B 版的意义。出问题时你能确定是「流程错了」还是「这一格自主得不对」。

### Step 5 的产物形态

配套项目正好就是第 1 步的样子 —— 图先定死，第 3 格的实现最后注入：

```python
def build_graph(check_fn):
    ...
    w.add_node("check_expense", check_fn)     # ← 只有这一格可换
    ...
    return w.compile()

app = build_graph(check_expense_fixed)        # A 版
app = build_graph(check_expense_autonomous)   # B 版 —— 图完全没变
```

**这个形态本身就是「协同」的答案**：把可变的部分收敛到一个函数体里。

## ↺ 迭代：图和工具互相拉扯

这一步最容易漏。**图和工具不是单向的，是互相拉扯的。**

| 发现 | 该做什么 |
|---|---|
| 某个「自主格子」的工具逻辑越来越复杂（查历史 → 多步推理） | 它可能不该做成工具，**该拆成独立节点** |
| 两个节点之间没有任何判断，只是连续操作 | **该合并** |
| 某格需要的工具，别的格子也需要 | 抽成公共工具（配套项目五个查询工具都在 `expense_common.py`） |
| 加了工具后某格从第 4 级升到第 3 级 | 回头检查下游的硬性规则还够不够用 |

---

## 完整检查清单

设计一张图时对照走一遍：

- [ ] **Step 0**：三条都满足吗？（阶段 / 传数据 / 不是全自主）
- [ ] **Step 1**：决策点找齐了吗？每个决策点带出哪些 State 字段？
- [ ] **Step 2**：每个 State 字段都有唯一写入者吗？有没有「没人读」的死字段？
- [ ] **Step 3**：每个节点边界上，三件事至少发生一件吗？节点名连起来念着像业务阶段吗？
- [ ] **Step 4**：每格的依据是第几级？有没有该用 L0 却用了 LLM 的？哪几格需要工具？
- [ ] **Step 5**：骨架跑通了吗？出 bug 时能定位到「流程」还是「某一格」吗？
- [ ] **↺**：加完工具后回去看，图要不要改？

---

## 本章小结

- **Step 0 最容易被跳过**：先问该不该上图
- **切入点不是「流程步骤」，是「决策点」** —— 它一次带出图、节点、State
- State 字段的 **唯一写入者** 是铁律
- 节点划分判据：判断 / 换自主度 / 传数据 —— **一件都没有就合并**
- **每格都要问「该不该用 LLM」** —— L0 是最容易被忽略的省钱机会
- 先全固定跑通，再升级自主
- 图和工具 **互相拉扯**，不是单向流程
